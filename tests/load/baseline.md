# 历史本机性能基线

> 历史记录：以下数字来自 2026-10-09 当时的代码、19 场景脚本及资源采样，保留原始结论供追溯。当前脚本已收敛到六核心接口、真实登录准备和原生 k6 HTML 报告；当前 Worker 已改为批量查询和 Redis Pipeline 同步，因此本文的“串行 Worker”诊断不能作为当前代码的结论。旧 JSON 与新版对照报告不兼容，复测请使用 [当前说明](./README.md)，不再按本文旧命令推断复现条件。

测量日期：2026-10-09。用途是确定当前代码在本机固定数据集下的可用负载、找到优化方向，并为后续复测提供对照。**这是单接口吞吐，不能相加，也不是生产容量承诺。**

## 环境与流程

- WSL2 / Linux 6.18.40.1，i9-13900HX，对进程开放 6 个逻辑 CPU，约 3.8 GiB 内存、4 GiB swap。
- Go 1.27、k6 2.3.0、MySQL 8.4.9、Redis 7.4。后端与 k6 同机；数据库运行在 Docker Desktop。保留 info 请求日志。
- 默认 MySQL 最大连接数 10、空闲连接数 10；API 与 Outbox Worker 共享连接池。InnoDB buffer pool 128 MiB，`innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`。
- 压测基线：200 用户、5 社区、2,000 帖子、20,000 评论、20,000 投票。数据与业务库隔离，但硬件资源共享。发帖正文 4 KiB，读取包含保留的旧帖和新帖。
- 19 个场景完成 1 RPS 冒烟、5 RPS 基线以及较高负载探测。缩小核心接口范围后，选取通过档位做 180 秒固定负载复测。短探测采用 5 秒升速、20–60 秒稳定阶段；结果只统计稳定阶段。
- HTTP 标准：p95 < 500ms、失败率 < 1%、业务检查成功率 > 99%、零 dropped iterations。发帖、删帖、投票还要求稳定施压时 Outbox 不持续增长。

所有轮次均恢复同一个 SQL 快照并重建 Redis DB13。初始化、JWT 签发、删除资源及会话准备均在计时外，每次迭代只有一个目标请求。完整步骤和参数见 [使用说明](./README.md)。

## 性能拐点与优化价值

### 1. 写请求的连接池与事务等待：有对照证据

默认 10 个 MySQL 连接，500 RPS 发帖探测 30 秒，p95 **2,120ms**，实际仅约 **408 RPS**，丢弃 **2,751** 次迭代。后端 CPU 峰值约 34%（一个 CPU 核为 100%），MySQL 容器约 32%，CPU 没有吃满。SQL 摘要中 COMMIT 13,493 次累计耗时 277.61 秒，平均约 **20.57ms**；累计耗时包含并发，不能当作墙钟时长。

仅将最大连接数调至 40，500 RPS 发帖持续 60 秒，p95 降为 **40.65ms**，实际达到 500 RPS，零错误和丢弃。这证明连接池配置对前台写吞吐有明显影响。两轮持续时间不同，优化效果是方向性证据；正式评估收益时应使用相同持续时间重复对照。

然而对照轮 Outbox 峰值仍达 **7,620**，最老事件 **15.26 秒**，只在停压后才排空，因此整条链路仍不通过。不要直接把连接数 40 当作最终优化方案：它会增加数据库并发，也不能解决后面的异步瓶颈。

同样的 2,500 RPS、60 秒、600 VU 帖子详情对照：10 个连接时 p95 589.63ms、实际 1943.43 RPS、丢弃 33396；40 个连接时 p95 132.87ms、实际 2496.65 RPS、丢弃 203。该对照也只改最大连接数；40 连接仍有丢弃，按零丢弃标准仍判失败。默认配置保持 10。


### 2. Outbox 投影处理：优先于继续提高 HTTP 吞吐

默认配置下，100 RPS 发帖、投票、删帖的 60 秒探测均通过，Outbox 峰值分别为 6、17、23，最老年龄均低于 0.54 秒。提高负载后：

| 场景 | RPS / 稳定秒数 | HTTP p95（ms） | Outbox 峰值 | 最老事件峰值（秒） | 停压后最终待处理 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `create_post` | 200 / 60 | 27.90 | 3347 | 16.509 | 0 |
| `vote` | 200 / 60 | 26.51 | 8329 | 41.656 | 0 |
| `delete_post` | 300 / 30 | 47.18 | 2054 | 6.817 | 0 |

上述轮次 HTTP 均通过，但施压期间待处理数量和最老年龄持续增长。停压后的最终数量为 0 不能证明负载可持续。发帖和投票的已测可用 / 不可持续档位分别是 **100 / 200 RPS**；删帖是 **100 / 300 RPS**。这是区间证据，尚未逐点找到精确极限。

代码中 Worker 每批取 256 个事件，按帖子合并后**串行**读取 MySQL、更新 Redis，再批量确认；它与 API 共享连接池。结合曲线，可以确认 Redis 投影处理链路是当前写负载瓶颈；尚无逐步骤计时或 profile，不能断言 Redis 本身慢，也不能把所有耗时归因于串行处理。

下一步有价值的是测量 Worker 的取批、读库、Redis 更新和确认耗时，优先评估减少往返、批量读取/更新以及 API 与 Worker 的连接资源分配。每次只改一个方向，用相同 HTTP 负载与 Outbox 曲线复测。扩大 Worker 并发需要验证同一帖子和用户的顺序、一致性与重试，不应只看事件消费数。

### 3. 注册与登录：CPU / bcrypt 成本

两者在 125 RPS、60 秒均通过；200 RPS、30 秒均失败：注册 p95 2,674ms、实际约 126 RPS，登录 p95 3,077ms、实际约 134 RPS。后端 CPU 峰值分别 572% 和 588%，已接近本机开放的 6 个逻辑核；k6 峰值低于 10%，MySQL 也未出现 CPU 饱和。

注册生成、登录校验 bcrypt（默认 cost=10）与这个 CPU 拐点一致，这是比“数据库可能慢”更明确的优化/容量证据。业务接口测试直接签发 JWT，把认证成本单独测量；部署时应按认证流量安排 CPU 与并发，避免业务每次请求都登录。没有据此降低密码哈希成本。

### 4. 读接口与评论：范围已经量化，具体内部耗时仍需定位

默认连接数 10，帖子详情与时间列表在 1,500 RPS、60 秒均通过；2,500 RPS、60 秒均失败：p95 分别约 590ms、536ms，实际约 1,943 / 2,296 RPS，并出现丢弃。负载器使用 600 个预分配 VU，失败轮 k6 CPU 未接近 6 核总容量，但服务变慢导致 VU 被占用，所以**失败档位不是精确后端吞吐上限**。p95 超标是独立的可用性失败证据。

刷新、退出、社区、其他列表变体、获取投票和评论列表在 500 RPS 短测均通过，记录为下界；没有对它们继续追逐极限。创建评论、回复、删除评论在 300 RPS、30 秒通过，500 RPS 超过延迟标准并发生丢弃；没有 Outbox，后续可优先检查事务等待和连接使用。

按 DIGEST 的 SQL 摘要未完整覆盖预处理查询。本次还保存了专用账号的 `statement/com/Prepare`、`statement/com/Execute` 执行统计；SQL 摘要没有对应查询不能证明查询没有成本。进一步细分读接口瓶颈，需要结合连接池 WaitCount/WaitDuration、执行统计与请求 profile，避免直接新增缓存或改索引。

## 复现、清理与限制

```bash
# 一条命令复现六个核心稳定档位（约 20 分钟）
make up
make loadtest-baseline

# 原始默认连接池：示例为稳定档位
make loadtest ENDPOINT=vote RATE=100 VUS=80 RAMP_SECONDS=0 HOLD_SECONDS=180
make loadtest ENDPOINT=post RATE=1500 VUS=600 RAMP_SECONDS=0 HOLD_SECONDS=180

# 单参数对照；不会修改 YAML 或业务库
BLUEBELL_MYSQL_MAX_OPEN_CONNS=40 make loadtest ENDPOINT=post RATE=2500 VUS=600 \
  RAMP_SECONDS=5 HOLD_SECONDS=60

make loadtest-reset
```

报告保存在本机 `tests/load/output/results/`，从该目录的 `README.md` 打开报告链接。已按确认范围保留六个核心稳定基线和十个瓶颈/连接池对照，删除冒烟、重复低负载及脚本验证结果；全业务接口的低负载和短探测结论保留在本文，部分轮次的原始文件已删除。

每轮保留参数、k6 JSON/HTML、终端摘要和 CPU/内存 CSV；发帖、删帖、投票另保留 Outbox CSV。历史容器 CPU/内存已合并进 `resources.csv`，关键 SQL 前后快照保留在对应轮次的 `diagnostics/`。普通请求日志不再保留；后续测试不再默认采集 SQL 快照，异常时保留错误日志样本，超过200行时保留首尾各100行并标记省略行数。HTTP 指标只有稳定阶段，Outbox 峰值包含升速及停压恢复的采样；每 2 秒采样一次，短暂峰值可能漏采。无需部署额外监控服务。

已按确认范围清理历史压测数据与测试残留：业务库保留 6 用户、4 社区、13 帖子、28 评论、29 投票；压测库复用保留的 1,000 帖子与 20,000 评论，补齐固定基线。清理前备份位于已忽略的 `tmp/cleanup-backup/`。已恢复压测基线，并清空集成测试留下的 MySQL 测试表、Redis DB14/15；业务 / 压测 Redis 全局排行榜分别为 13 / 2,000 条，压测服务已退出。

验证通过：`go test ./... -count=1`、`go vet ./tests/load/data`、Shell/Python 语法检查、19 个场景冒烟、六个核心场景的 3 分钟复测，以及最终版启动/采样/退出流程。另验证了空压测库初始化，并恢复原 SQL 快照；配置误指向业务库或 Redis DB0 时会被拒绝，专用 MySQL 账号不能读取业务库。没有修改业务代码或默认连接池。

未覆盖真实流量比例、冷热热点分布、生产数据规模、跨机网络或长时间 soak 测试。单机结果受 Docker Desktop、日志、数据库持久化和硬件资源共享影响。后续优化应保持基线、负载参数和运行环境一致，先比较 p95/p99、实际成功 RPS、错误/丢弃和 Outbox 趋势，再讨论收益。
