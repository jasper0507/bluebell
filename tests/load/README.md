# 本机压测

目标：找出哪个接口在什么负载下变慢，并用相同条件验证优化效果。单接口覆盖注册、登录、帖子详情、时间列表、发帖、投票六个核心场景；业务混合负载额外覆盖热榜、评论列表、当前投票状态和发表评论。日常施压、HTTP 结果统计和 HTML 报告使用原生 k6，无 npm 依赖、远程脚本、k6 扩展或 Python 采样；另行归档的深度诊断可使用本机采样工具，不改变正式施压脚本。

## 日常操作

```bash
make up
# 新环境且没有 output/state/baseline.sql 时，先 make loadtest-init
make loadtest-smoke  # 六接口低负载验证，不用于简历性能数字
make loadtest-probe  # 逐档加压，每档 10 秒升速 + 60 秒稳定施压
```

**打开 `tests/load/output/results/index.html`。** 总览给出已测通过/失败档位；点“查看”打开单轮中文报告，再点“打开 k6 原生交互图表”看请求速率和响应时间。发帖与投票的报告还直接展示后台积压曲线。

当前实测数字、限制和后续优化方向见 [压测发现](./findings.md)。

## 业务混合负载

```bash
# 先验证完整业务链路；冒烟不判后台容量
make loadtest-mixed RATE=100 RAMP_SECONDS=0 HOLD_SECONDS=20 VUS=150
# 一轮 30 秒升速 + 10 分钟稳定施压
make loadtest-mixed
# 逐档反馈校准 VU、探测并验证最高通过档；结束自动恢复测试快照
make loadtest-mixed-probe
make loadtest-reset
```

`RATE` 默认 1000，是完整执行时的预期 HTTP 请求数/秒，必须为 20 的正整数倍。脚本按以下用户流程独立设置到达率，而不是随机调用孤立接口；响应变慢不会自动降低计划到达率。`RAMP_SECONDS` 默认 30、`HOLD_SECONDS` 默认 600；受访问令牌有效期约束，升速 + 稳定 + 120 秒必须小于 900 秒，不适用于长时间 soak 测试。

| 用户流程 | 1000 RPS 下的次数/秒 | 顺序请求 |
| --- | ---: | --- |
| 游客浏览 | 180 | 时间列表或热榜 → 详情 → 评论列表 |
| 浏览并投票 | 60 | 列表 → 详情 → 评论列表 → 当前投票状态 → 投票 |
| 发表评论 | 20 | 详情 → 评论列表 → 发表评论/同帖回复 → 再读评论列表 |
| 发帖 | 10 | 登录 → 发帖 → 新帖详情 → 时间列表 |
| 老用户登录 | 30 | 登录 |
| 新用户注册 | 5 | 注册 → 使用新账号登录 |

完整流程下的预期接口比例：时间列表 19%、热榜 6%、详情 27%、评论列表 28%、当前投票状态 6%、投票 6%、发表评论 2%、发帖 1%、登录 4.5%、注册 0.5%。浏览列表按 3:1 使用时间/热度排序。列表 80% 访问前三页，其余访问第 4–20 页；列表浏览后 80% 进入热门收藏/分享链接，其余点击当前列表响应中的帖子。热点固定为准备阶段热榜前两页的 20 篇帖子；发表评论流程同样以 80% 概率选择热点。各步骤始终关联同一帖子，请求间思考时间为 0.2–0.8 秒。这是业务假设，不是线上日志推导的比例。

使用基线 200 个账号准备真实登录令牌，正式发帖流程重新登录，注册流程使用新账号登录；准备登录不计入正式数字。投票根据当前状态执行赞成、反对、取消，尽量避免相同状态空操作；账号会被多个并发流程复用。评论正文约 600 字节，25% 尝试回复当前帖已有评论；发帖正文为 4 KiB。数据随注册、评论和发帖增长，不在稳定窗口中恢复。

**逐接口验收**：每个接口分别要求 p95 < 500ms、HTTP/业务失败率均 < 1%，同时展示 p99、请求数、实际/成功 RPS；总体 p95 达标不能替代逐接口达标。流程按开始时间分组，整轮还要求稳定阶段全部已开始流程完成、无丢弃流程、Outbox 未见持续积压。`dropped_iterations` 的单位是整个流程，包含升速阶段，不分摊成虚构的逐接口丢弃数。前置失败会停止依赖请求，实际请求比例与预期比例可能不同，必须一起看完成率和实际 RPS。

请求根据开始时间标记准备/升速/稳定/收尾阶段；稳定窗口中开始的请求完成后计入 HTTP 指标，窗口结束后新发出的请求不计入。流程最多收尾 30 秒，每个请求超时 5 秒；稳定窗口中开始的流程包含收尾结果。`VUS` 按流程到达率比例分配，向上取整且每流程至少 5 个；实际分配量记在摘要和报告中，VU 表示执行槽位，不表示独立账号数量。

### 逐档动态校准与独立判定

`make loadtest-mixed-probe` 先在 100 RPS 稳定 60 秒采集初始流程耗时，再按 400 → 600 → 800 → 1000 RPS 探测。每档先升速 10 秒、稳定 30 秒校准，配额在轮次之间反馈调整；最多调整三次，正式 60 秒轮次期间配额固定。正式轮施压未校准时将该轮反馈到同档校准，短校准、60 秒正式轮和十分钟正式轮的反馈合计最多调整三次；完整施压下的服务/后台首次未通过，或校准额度用完，即停止升档。400 未通过时补测 200；最高通过档保留同档已验证配额，再短校准后进行 30 秒升速 + 600 秒验证。没有通过档、施压器资源不足或校准失败不会继续升档。校准以 `LABEL=calibration` 记录，不混入正式容量区间；批次目录保存每次输入证据、配额、占用和调整决定。结束自动恢复独立测试库和 Redis DB13，历史证据保留。

新增 `MIXED_VUS` 为完整 JSON 映射，键为 `guest/member/commenter/publisher/returning/newcomer`，值必须为正整数；提供后覆盖混合场景的总 `VUS` 比例分配，单接口不受影响。未提供时保留旧 `VUS` 行为。例：

```bash
make loadtest-mixed RATE=100 RAMP_SECONDS=10 HOLD_SECONDS=60 LABEL=calibration \
  MIXED_VUS='{"guest":32,"member":22,"commenter":12,"publisher":10,"returning":8,"newcomer":6}'
```

成功和失败流程分别记录样本数、完整耗时均值、中位数、p95/p99/max，包含思考时间和收尾；零样本耗时为空。预分配初值为 `ceil(当前档流程到达率 × 成功流程平均秒数 × 1.4) + 5`，至少 5 VU；少于 30 个成功样本时，耗时采用观测最大值与 `思考次数 × 0.8 秒 + 请求次数 × 0.5 秒` 启动预算的较大值。这个预算只帮助启动校准，不是服务容量承诺。**p99 仅参考，不用于确定配额**。每个档位都重新观测，不能将 100 RPS 的低频样本直接外推为最终配额。

平均占用率为流程实际占用稳定窗口的时间总和 / 窗口时长 / 流程配额；包括跨入和跨出窗口的占用，不能称为峰值。校准要求完整施压且各流程平均占用率 ≤75%；出现丢弃、流程开始数不足或占用率 >75% 时受影响流程至少增加 25%，并与当前档实际耗时推荐量取较大值。同档确实出现丢弃时，还与 `ceil(本档最长成功流程秒数 × 到达率 × 1.2) + 5` 取较大值，以吸收已观测的尾部；此值仅用于当前档反馈，不外推到其他档位。每次调整重新恢复快照、短测验证，再复测原正式窗口；短校准、60 秒和十分钟反馈共享每档三次调整额度。资源不足或额度用完停止，不能靠无限增加 VU 掩盖问题。

`resources.csv` 约每两秒采一次：服务/k6 在 WSL `/proc` 读取 CPU 和 RSS，MySQL 在容器内 `/proc/1` 读取并确认进程名为 mysqld，避免 Docker/WSL PID 命名空间误配；容器读取和 Outbox SQL 都有观测开销。CPU 单位为占用核数，host 为整机忙碌比例；可用内存来自施压主机。正式判定至少需要每个来源三个稳定样本。稳定阶段至少三个样本可用内存低于 `max(256 MiB, 总内存 10%)`，或 k6 占用 ≥可用核数 80%，保守标记施压器资源不足，停止加码。这些阈值是本机施压保护，不是性能根因证据。

报告和 `assessment.json` 分别记录：

- 施压：资源采样足够、未触发保护、无丢弃，各流程实际开始数至少为 `floor(计划次数)−1`；允许一条开始边界的计时差。否则标记施压未校准、资源不足或采样不足。
- 服务：十个接口独立验收、稳定开始流程全部成功完成，Outbox 单独判定。服务结果与施压失败可以同时出现；施压不足时结果只描述实际收到的负载，不能证明完整承载目标档位。

台账追加 `generator_status/service_http_pass/mixed_allocation` 字段；流程 CSV 增加成功/失败耗时、样本数和占用率。历史摘要、标签与测量数值不改写，未采集资源的历史轮次显示“历史样本未校准”并保留原判定。

评论按升序分页，发表评论后的列表回读仅检查总数增长，不证明新增评论 ID 在当前页。发帖后检查 MySQL 详情，列表检查合法数据，不要求新帖立即出现在首屏；异步投影由 Outbox 采样另验，本轮不测逐事件可见延迟。删除、刷新令牌、退出登录、社区导航未包含在本模型中。

每轮 `report.html` 展示逐接口与流程表，并导出 `endpoints.csv`、`journeys.csv`。总台账 [records.csv](./records.csv) 保留混合轮次；[mixed-records.csv](./mixed-records.csv) 保存逐接口数值，生成全量总览时只追加新轮次，已有行原样保留。完整证据仍在原始轮次目录。`loadtest-compare` 不对混合总体 p95 计算优化收益，需按接口与流程单独比较。

当前稳定通过下界为混合负载 1000 RPS × 10 分钟（790 VU、零错误/丢弃）；1200/1400 RPS 仅有 60 秒短测通过，1400 两次十分钟均未通过。正式 A/B、证据强度与遗留问题统一见 [当前压测结论](./findings.md)。

## 测试台账与分类

[新版逐轮台账](./records.csv) 保存每轮数据，随完整 HTML 总览自动追加新轮次；`make loadtest-report` 可从原始摘要重新生成总览。已有轮次附件（包含报告、assessment 和判定文件）保留，不重写历史证据；重复生成不会重复追加台账。台账位于 output 目录之外，可纳入 Git；原始 HTML、JSON、日志与 Outbox 曲线仍须保留，CSV 不替代原始证据。[历史逐轮台账](./records-history.csv) 单独保存旧格式数据，不参加新版百分比对照。已经删除的历史原始轮次无法补回，只能引用 [历史基线](./baseline.md) 中明确保留的汇总。

分类为冒烟、容量探测、稳定负载、诊断、优化前、优化后。`LABEL=before/after` 仅表示待配对阶段，不代表已满足可比条件；稳定窗口不足 30 秒优先归为冒烟；其他非 `current` 标签归为诊断，例如 `LABEL=diagnostic` 或 `LABEL=calibration`。正式对照的三轮目录与改动说明另记在 [压测发现](./findings.md)，脚本定稿前的诊断轮次不混入正式基线。

每轮记录接口、目标与成功 RPS、VU、升速与稳定时长、p95/p99、HTTP/业务失败率、丢弃、退出码、HTTP/后台判定、稳定阶段后台峰值，以及代码、脚本、数据快照、配置、环境和报告路径。CSV 的失败率是 0–1 小数，延迟单位为毫秒，后台年龄单位为秒；空值表示缺失或不适用，不表示零。成功、失败和运行异常均保留。服务启动失败等未生成摘要的运行，需手工在发现文档记录命令、时间、失败原因和日志路径，不能算性能样本。

后续每次优化同时更新发现文档：改动目的与范围、每轮执行命令和报告目录、结果、是否可比及剩余问题。功能回归、`go vet`、报告工具校验等另记为正确性验证，保留命令、退出码和关键输出，不混入性能提升计算。实际回归使用 `go test ./... -count=1`，缓存命中只记为缓存结果。`go.mod` 的 `ignore ./tests/load` 让 `./...` 跳过本目录，数据工具需另用 `go vet ./tests/load/data` 检查；压测脚本构建时仍会显式编译它。

最终分别计算每项优化相对其直接基线的收益，以及最终版本相对最初基线的累计收益；百分比不能相加。延迟降低率 = `(优化前三轮中位数 − 优化后三轮中位数) / 优化前三轮中位数 × 100%`；经正式复测通过的吞吐提升率 = `(优化后通过档位 RPS − 优化前通过档位 RPS) / 优化前通过档位 RPS × 100%`，只能称为已验证吞吐下界的提升。基线为零时不计算百分比；变慢或退化如实记录。最终给出原始轮次链接、条件、绝对数值、百分比与可直接用于简历的表述。

只查一个接口或指定探测档位：

```bash
make loadtest-probe ENDPOINT=create_post RATES='50 100 200 300'
make loadtest ENDPOINT=post RATE=1000
```

默认探测档位：注册/登录 100、150、200 RPS；详情/列表 1000、1500、2000、2500 RPS；发帖/投票 100、200、300、500 RPS。每个接口遇到首次未通过就停止加压，然后测试下一个接口；运行异常直接停止。默认全套可能需要约半小时以上，取决于在哪档失败以及数据恢复速度。

`make loadtest-baseline` 是六接口各 180 秒的参考负载检查：注册、登录、发帖、投票为 100 RPS，详情、列表为 1000 RPS。这些是待验证的参考值，不是容量结论。任何一轮未通过即停止。

## 优化前后对照

先从探测结果选一个确有问题的接口，保持相同目标速率、VU、时长、数据快照和环境：

```bash
# 例：在修改代码或配置前，记录三轮
make loadtest-repeat ENDPOINT=create_post RATE=200 VUS=155 LABEL=before
# 完成一个明确的优化后，按完全相同参数记录三轮
make loadtest-repeat ENDPOINT=create_post RATE=200 VUS=155 LABEL=after
```

每轮稳定施压 180 秒，默认升速 10 秒。预期阈值失败也会保存结果并完成三轮；其他运行错误立即停止。

优化完成后需要重新测旧版本时，先创建独立 checkout，再通过 `SERVER_SOURCE_DIR` 指定待测服务源码。数据准备工具、配置、快照、施压和报告仍统一使用当前目录；每轮提交号记录待测源码的提交，程序指纹记录实际服务二进制。例如：

```bash
git worktree add --detach /tmp/bluebell-outbox-before-3eb934a 3eb934a
make loadtest-repeat ENDPOINT=create_post RATE=200 VUS=155 RAMP_SECONDS=10 LABEL=before \
  SERVER_SOURCE_DIR=/tmp/bluebell-outbox-before-3eb934a
make loadtest-repeat ENDPOINT=create_post RATE=200 VUS=155 RAMP_SECONDS=10 LABEL=after
```

数据准备或测量脚本变化后，旧脚本指纹的历史轮次不能直接配对；前后两组应使用同一套脚本重新测量。

把终端打印的六个结果目录填入下列命令：

```bash
make loadtest-compare BEFORE='优化前目录1,优化前目录2,优化前目录3' \
                      AFTER='优化后目录1,优化后目录2,优化后目录3'
```

命令会打印对照 HTML 路径。报告展示六轮 p95 和实际成功 RPS 的柱状图，以及三轮 p95 中位数的变化比例；写接口另比较稳定阶段后台待处理峰值和最老事件等待峰值；不会只挑最好的一轮。负载、时长、脚本、环境或数据不同，会拒绝给出提升比例。同一版本的三轮代码/配置也必须一致。前后配置变化会单独标注；代码与配置都没有变化时，差异只能算测量波动。

可将上一次优化的三个 `after` 目录直接传给新对照的 `BEFORE`，无需重新测旧版或改写原始摘要。对照展示按 `BEFORE` / `AFTER` 参数分组，两组必须各三个目录；原始标签与完整台账保持不变，可比性检查仍然执行。2026-10-11 删除优化的复测已复用 `20ef3c1` 的正式结果，详见 [删除优化复测](./history/2026-10-11.md#outbox-删除优化复测2026-10-11)。

**固定负载的 RPS 通常不会增加。** 如果要证明吞吐提升，需在优化前后分别重新探测通过档位，再在选中的档位正式复测。不能把目标 RPS、短测峰值或有丢弃的轮次写成最大可用吞吐。

## 怎么判断需要优化

| 报告信号 | 含义与下一步 |
| --- | --- |
| p95 ≥ 500ms | 约 5% 请求更慢，超出本项目初始标准；检查该接口内部耗时 |
| HTTP / 业务失败率 ≥ 1% | 先排查失败响应、鉴权、数据或服务错误 |
| 丢弃请求 > 0 | k6 没有发出全部计划请求；检查 VU、服务变慢和同机资源竞争，不能当作精确后端上限 |
| HTTP 达标但后台持续积压 | 写链路仍未通过；检查 Outbox Worker、共享连接池及投影处理 |
| 本档通过 | 只证明当前条件下这一档通过，没有证据要求优化 |

认证接口变慢时优先核对 bcrypt 的 CPU 成本；读写接口变慢时先检查连接池等待、查询和事务耗时。这些是排查方向，**k6 本身不能证明具体 SQL、Go 函数或 Redis 是根因**。本轮不自动修改业务代码或连接池。

HTTP 标准为 p95 < 500ms、HTTP 和业务失败率均 < 1%、丢弃为 0。准备阶段真实登录和数据检查不计入正式数字；单接口模式稳定阶段每次迭代只有一个目标请求。成功 RPS = 稳定阶段业务成功数 / 稳定秒数。请求最多等待 5 秒，单接口收尾最多 5 秒，混合流程收尾最多 30 秒。

Outbox 每两秒通过 SQL 采样一次。报告分别画待处理数量和最老等待时间；0 秒为稳定施压开始，负数是准备/升速，稳定秒数之后是停压恢复。自动检查仅作保守筛查：稳定样本至少 10 个；末三分之一相对首三分之一，待处理数中位数增加 > 10 且等待年龄增加 > 1 秒，标记“持续积压”；没有重试、等待始终 ≤ 1 秒且数量增长 ≤ 10，标记“未见持续积压”；其余标记“需确认”。样本不足的冒烟不判后台容量；正式测试需确认也算未通过。停压后归零不能证明施压期间可持续。

Worker 的实际确认吞吐需单独测量：使用成功提交后 DELETE 的实际 `RowsAffected`，按 COMMIT 完成时间归入稳定窗口，再除以稳定秒数；不能用读取数量、尝试确认数量或 HTTP 成功数代替。批次阶段计时应拆开取数、合并、帖子/投票查询、Redis、重试和确认，再将确认拆成事务开始、DELETE 调用和 COMMIT；跨窗口的阶段占用按时间区间裁剪。

2026-10-11 的隔离诊断与单变量验证见 [历史 Worker 诊断](./history/2026-10-11.md#worker-分阶段诊断与确认删除验证2026-10-11) 和 [批次报告](./output/results/outbox-worker-20261011/report.html)。完整批次 CSV、计时补丁、MySQL 采样及离线分析保存在该结果目录；临时插桩已撤下，单轮 `LIMIT` 探针不算正式三轮 A/B，也没有合入业务代码。

后续 [执行计划与阻塞事务报告](./output/results/outbox-plan-20261011/report.html) 捕获了实际 DELETE 连接的优化器 trace：部分语句因估算成本放弃 PRIMARY 范围访问；可控两事务复现确认了投票事务插入新事件造成的集合外锁等待。**LIMIT 不保证精准访问：目标中有一个 ID 已不存在时，仍可扫描并等待集合外记录。** 复现源码、三次日志和逐条计划 CSV 均归档，详细边界见 [DELETE 实际计划与阻塞事务追踪](./history/2026-10-11.md#delete-实际计划与阻塞事务追踪2026-10-11)。

总览是 `output/results/index.html`；每轮有 `report.html`（中文结论）、`charts.html`（k6 原生交互图表）、`summary.json`、`k6.log`、诊断 `server.log`；写接口与混合负载另有 `outbox.csv`。普通 info 请求日志不长期保存，诊断只保留最后 200 行。结果目录名包含时间、版本标签、接口和速率。图表采样周期 2 秒；测试必须超过三个采样周期才有完整图表。历史报告保留在原目录和 [baseline.md](./baseline.md)，不能与新版摘要混用。

分享中文报告时保留整轮目录，`report.html` 会引用同目录的 `charts.html`；原生 `charts.html` 可单独分享。

每轮记录代码提交与服务程序指纹、测量脚本指纹（不包含离线 HTML 排版）、有效服务配置、快照指纹、数据数量、机器与 Go/k6/MySQL/Redis 版本；不保存访问令牌或服务密码到报告。`make loadtest-report` 可重新生成新版总览。

服务/数据准备由短 Shell 编排和 Go 数据工具完成；Go 负责首次初始化、被测版本迁移与 Redis 基线重建，不做施压、鉴权或报告。已有快照复用，无需重新初始化。每轮恢复 **200 用户、5 社区、2000 帖子、20000 评论、20000 投票**；详情随机取帖子，列表遍历前 20 页，发帖正文 4 KiB。使用独立 MySQL `bluebell_k6_verify`、Redis DB13 和端口 18080，业务库和 Redis DB0 不参与恢复。

快照 `output/state/baseline.sql` 只保存数据，INSERT 显式列名以适配不同版本的字段顺序。每次恢复先删除并重建独立库 `bluebell_k6_verify`（utf8mb4 / utf8mb4_unicode_ci），再使用 `SERVER_SOURCE_DIR` 指向的被测版本执行 `cmd/migrate` 生成表结构，然后导入数据并重建 Redis DB13 投影。旧完整快照保留在 `output/state/baseline-schema-v1.sql`。

## 简历数字怎么写

优先引用“相同本机环境、固定数据集、每轮 3 分钟、重复 3 轮，在 X RPS 下，p95 中位数由 A ms 降至 B ms，降低 C%，优化后失败率 < 1%、无丢弃，写接口无持续积压”。数字必须来自完整对照，未完成优化前后测量时只能写当前通过的负载和延迟。写链路还可以引用相同负载下“最老待处理事件等待峰值从 A 秒降至 B 秒”；这是两秒采样的积压年龄指标，不能称为每条事件完成耗时的 p95。

本机后端、k6、MySQL、Redis 共享硬件；接口吞吐不能相加，结果不是生产容量承诺。没有覆盖生产数据规模、真实流量比例、跨机网络或长时间持续运行。
